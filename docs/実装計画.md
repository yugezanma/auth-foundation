# 実装計画: v1.0.0

[設計.md](設計.md) の §8 段階1(このリポジトリで v1.0.0 のタグを付けるまで)の手順。ブランチ `feature/v1` で作業し、手順ごとにコミットしてプッシュする。各アプリのリポジトリは変えない。

## 前提

- Python 3.11 以上(標準ライブラリだけ。テストは `python -m unittest`。pytest は使わず、依存を持たない)
- Node 20 以上(依存なし。テストは `node --test`)
- 判定テスト(`spec/vectors/*.json`)が正。Python 版と JS 版はどちらも、すべての判定テストを通す

## 手順

### 1. 骨組み

- `README.md`(何のリポジトリか、各アプリでの使い方、テストの流し方)、`VERSION`(`1.0.0-dev`)、`CHANGELOG.md`、`.gitignore`
- テストの入口: `python -m unittest discover -s python/tests`、`node --test js/test/`。両方をまとめて流す `tools/check.sh`

### 2. 判定テスト(`spec/vectors/`)

先に正解を書き、部品はあとから合わせる。1ファイル = 1つのテーマ。

| ファイル | 中身 |
|---|---|
| `catalog.json` | `validate_catalog`: 正しいカタログ、未知の機能・動詞、`member`・`audit` が無い、key の重複 |
| `basic.json` | 直接の割当、`org` と `site` の範囲、組織全体の操作に `site` の割当は届かない |
| `union.json` | 2つのロールの和集合。`rank` が低いロールだけが持つ権限も残る(SolarOM の back_office の例) |
| `teams.json` | チーム経由、直接とチームの両方から届く経路の並び順と重複の扱い |
| `groups.json` | グループの範囲、1つの拠点が2つのグループに属する |
| `exclusions.json` | 除外リスト(拠点、グループ)。除外は割当ごとで、ほかの割当からは届く |
| `lifetime.json` | `expires_at`・`revoked_at` の境目(`now` と同じ時刻は「過ぎた」)、null は有効 |
| `membership.json` | 停止中・招待中・所属なし → `not_member` |
| `reasons.json` | `out_of_scope` と `no_permission` の見分け |
| `reserved.json` | `collaboration` の割当、`equipment` の範囲は効かない |
| `errors.json` | 未知の拠点・ロール・ユーザーの扱い(ユーザーが未知なら `not_member`、拠点・ロールが未知ならエラー) |
| `helpers.json` | `permissions_at`・`sites_with` |
| `guard.json` | `check_guard`: `no_admin_left`、`self_lockout`、チーム経由の管理者、問題の無い変更 |
| `audit.json` | `make_audit_event`・`validate_audit_event`: 正しい記録、必須の項目が無い、未知の操作名、`app.` の操作名、秘密のキー(入れ子の中も)、日時の形 |
| `pda.json` | 電力データ集計の4人(設計.md §7-4)× 6契約 × 操作。今の `can_operate`・`is_admin`・断る理由と同じ結果になること |
| `solarom.json` | SolarOM の `perm-data.js` のデータ(割当 a1〜a11、拠点は判定に効く分だけ抜き出す)。`permissionsAt` と同じ結果になること |

- 判定テストの形を `spec/vectors.schema.md` に書く(`call` ごとの `args` と `expect`)
- 監査ログの操作名の一覧は `spec/audit-actions.json` に置き、両方の版はこれと同じ一覧を持つ(写しの際にテストで突き合わせる)

### 3. Python 版(`python/auth_foundation/`)

- `catalog.py`(`validate_catalog`)、`evaluate.py`(`evaluate`・`permissions_at`・`sites_with`)、`guard.py`(`check_guard`)、`audit.py`(`make_audit_event`・`validate_audit_event`・操作名の一覧)、`errors.py`(エラーの種類)、`__init__.py`(公開する名前と `__version__`)
- 入力は dict / list(JSON をそのまま読んだ形)。戻り値も dict(`Decision` は dict にし、JSON の正解とそのまま比べられるようにする)
- テスト: `python/tests/test_vectors.py`(全ての判定テスト)、`test_python_only.py`(引数の型の誤りなど、言語ごとの扱い)

### 4. JS 版(`js/auth-foundation.mjs`)

- 関数の名前は JS の慣習に合わせて camelCase(`evaluate`・`permissionsAt`・`sitesWith`・`checkGuard`・`validateCatalog`・`makeAuditEvent`・`validateAuditEvent`)。判定テストの `call` は snake_case で書き、JS のテストで読み替える。引数・戻り値のキーは JSON と同じ snake_case
- ES2017 の範囲で書く(ビルドしない)。`Date`・`Math.random` を使わない。時刻の比較は ISO 8601 を解いて行う(`now` を引数で受ける)
- テスト: `js/test/vectors.test.mjs`

### 5. 写し取り用のスクリプト(`tools/vendor.py`)

- `--lang python|js`、`--dest <置き場所>`。置き場所に `auth_foundation/` を作り、部品・判定テスト・`VERSION`・`MANIFEST.json`(ファイルごとの SHA-256、もとのタグとコミット)を置く
- 作業ツリーに未コミットの変更がある、または HEAD にタグが無いときは止める(`--allow-dev` で開発中の版を写せるが、`VERSION` に `-dev` が残る)
- 置き場所にすでに写しがあれば、置き換える前に、写しが手で直されていないか(`MANIFEST.json` と一致するか)を確かめ、直されていれば止める
- 各アプリのテストにそのまま入れられる確認用のコードも写す: `verify_vendor.py`(Python。ハッシュの一致と全判定テスト)、`verify-vendor.mjs`(JS。同じ)
- テスト: 一時フォルダへ写し、確認用のコードが通ること、1バイト変えると落ちること

### 6. 仕上げと v1.0.0

- `README.md` に各アプリでの取り込み手順(写す、テストに確認用のコードを足す、版を上げるとき)を書く
- `VERSION` を `1.0.0` にし、`CHANGELOG.md` を書く
- `/code-review` で見直す
- ユーザーの確認を得てから main に入れ(PR を作るかはユーザーに聞く)、`v1.0.0` のタグを付けてプッシュする

## 終わったときの状態

- `tools/check.sh` で、Python 版と JS 版の両方がすべての判定テストを通る
- `pda.json` で電力データ集計の今の判定と一致すること、`solarom.json` で SolarOM の今の判定と一致することが確かめられている
- `v1.0.0` のタグがあり、各アプリのセッションで `tools/vendor.py` を使って取り込める
