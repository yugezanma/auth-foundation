## 1. 決めたこと

| # | 論点 | 決定 |
|---|---|---|
| 1 | 何を共通にするか | **仕組み**(仕様・判定の部品・判定テスト)まで。**利用者のデータは別々**にし、データベースも認証サービスの契約もアプリごとに持つ。両方のアプリを使う人はいないので、シングルサインオンは作らない |
| 2 | 共通仕様のもと | SolarOM の **Mem 権限モデル**。電力データ集計はその一部として当てはめる(テナント=SaaS を契約する会社、範囲=契約、作成者=担当契約の範囲で操作できるロール。§7) |
| 3 | ログインの方法 | **アプリごとに別にする。** 電力データ集計は今のメールアドレス+パスワード+メールのワンタイムコード(`auth_provider = password`)のまま。SolarOM は外部の認証サービスを OIDC で使う(`auth_provider = oidc`)。共通仕様では**ログインした後の約束**だけを決める(§5) |
| 4 | 共通仕様の範囲 | **SolarOM のデモ P1 が使っている範囲+期限・失効**を中核とする。principal はユーザーとチーム、範囲は組織全体・グループ・拠点、除外リストあり、和集合。協力会社・オーナーのテナント(collaboration)と設備の範囲(equipment)は、**データの形と名前だけを予約する**(§3-5) |
| 5 | 部品の配り方 | このリポジトリで**版のタグ**を付け、各アプリには**写し**(vendoring)を置く。写しの中身はハッシュと判定テストで確かめる(§6) |
| 6 | 監査ログ | **項目と必須の操作**を共通にする。業務の記録(取込・PDF など)を残すかは各アプリが決める。部品には「記録の形を作り、形が正しいか確かめる」関数だけを入れ、保存は各アプリで行う(§4) |
| 7 | 電力データ集計の取り込み順 | `feature/user-management` を**今の形のまま先に main に入れる**。共通の形への移行はその後に別のブランチで行い、今のテストがそのまま通ることで振る舞いが変わらないことを確かめる(§8) |
| 8 | このリポジトリの git | 最初の設計書は main に直接入れる。以後はブランチで作業し、区切りごとにコミットしてプッシュする。PR はユーザーが求めたときだけ作る。各アプリのリポジトリは、それぞれのセッションで変える |
| 9 | 課金(両方のアプリとも拠点数で課金する) | **判定には入れない。** 課金は「契約上、テナントに何が許されるか」で、判定が答える「この人がこれをしてよいか」とは別の問いのため。共通にするのは、拠点の増減の記録、課金に効く操作を守る規約、課金しないテナントの予約まで(§3-7) |
| 10 | 電力データ集計のテナント(2026-11-02) | **会社ごとにデータを分ける。** テナントは SaaS を契約する会社(病院向けに月次レポートを作る省エネサービス会社)。病院はレポートを受け取る側で、テナントではない(病院が自分で見る画面は後で作る。そのときは予約の `owner` を使う)。拠点数はテナントごとに数えて請求する(§7-1) |
| 11 | 1人が入れるテナントの数 | 共通の形は Mem のとおり、**ユーザーは全体で1人1つ、所属はテナントごと**(複数持てる)。電力データ集計は**1人1社**に限る(所属を1つだけ作る)。ログインは今のままメールアドレスでユーザーを探し、所属のテナントに入る。あとで複数にするときは、ログインのあとにテナントを選ぶ画面を作る(§5) |

| 13 | テナントの作り方 | **当社が契約のあとに作る。** 運営側がテナントを作り、お客様の最初の管理者を招待する。そのあとのユーザーは、お客様の管理者が足す(§3-8) |
| 14 | サポートの許可の期限(2026-11-11) | 許可する人が選ぶ。**既定7日・上限30日**(§3-8) |
| 15 | 運営側のログイン(2026-11-11) | Web の画面へのログインはお客様と同じで、**運営側の人のセッションは2時間**。**テナントの作成・停止・再開はクラウドの権限で守られたコマンドだけ**で行い、画面には置かない(§3-8) |
| 16 | 運営側の守り(2026-11-13) | 電力データ集計の段階 3c で足されたものを共通にする。①運営側の人は**ログインのたびに2つ目の確かめ**(電力データ集計ならメールのコード)をし、端末を覚えて省く仕組みを使わせない。②運営側の人の**接続元を IP で限れる**ようにする。③サポートの閲覧中も、**お客様の管理者だけの画面**(ユーザー管理・監査ログ・サポートの許可)は見せない(§3-8・§5) |

**やらないこと**: シングルサインオン、利用者データの共有、共通の認証サーバー、パスワードやワンタイムコードの共通の部品(電力データ集計の中に残す)、画面の部品(画面は各アプリが作る)、データの状態による絞り込み(Mem §7 の7段目。§3-4)、課金の計算・請求・プランの上限(§3-7)、お客様の申し込みでテナントを自動で作ること(§1 の 13)。

- 部品は**副作用を持たない関数**だけにする。データベース・Cookie・画面・メールには触らない。入力はすべて引数で受け取り、時刻も引数(`now`)で渡す。SolarOM の「Math.random / Date を使わない」決定論の規約とそろえるため、判定テストでも結果が変わらないようにするため

## 3. 権限の形と判定

### 3-1. 言葉とデータの形

Mem 権限モデル §1〜§4 の形を共通にする。表の名前と列は**論理的な形**で、各アプリは自分のデータベースに合わせて持ってよい(判定には §3-3 のスナップショットの形で渡す)。

| 共通の言葉 | 意味 | 電力データ集計 | SolarOM |
|---|---|---|---|
| テナント(`tenant`) | データの持ち主の単位。種類(`kind`)は §3-8 | SaaS を契約する会社(省エネサービス会社) | 会社 |
| ユーザー(`user`) | 人。`id`・`email`・`name`・`auth_provider`(`password` / `oidc`)。**全体で1人1つ**で、メールアドレスは全テナントで重ならない | ユーザーID・メールアドレス・名前 | 同じ |
| 所属(`membership`) | ユーザーとテナントの関係。`status` は `invited` / `active` / `suspended`。1人が複数のテナントに所属できる形にする | 有効 = `active`、無効 = `suspended`。**1人1つ**に限る | 同じ(協力会社の人は複数を持ちうる) |
| 機能グループ(`feature`) | 権限の大きな単位 | §7-2 | `inspection` など7つ |
| 動詞(`action`) | `view`(閲覧)/ `create`(起票)/ `edit`(編集)/ `approve`(承認)の4つで固定 | 同じ | 同じ |
| 権限(`permission`) | `feature.action` の形(例: `report.edit`) | 同じ | 同じ |
| ロール(`role`) | 権限の組。`key`・`rank`・`audience`・`perms` | 3つ | 5つ(P1) |
| チーム(`team`) | ユーザーの集まり | 使わない | 使う |
| 範囲(`scope`) | `org`(組織全体)/ `site_group`(グループ)/ `site`(拠点) | 組織全体・**契約** | 組織全体・エリア・発電所 |
| 割当(`assignment`) | principal × ロール × 範囲。除外リスト・期限・失効を持つ | §7-3 | `ASSIGNMENTS` |

**共通で必ず持つ機能グループ**: `member`(メンバー・権限)と `audit`(監査ログ)。ほかの機能グループは各アプリが決める。

**削除の扱い**: 削除は権限として持たない。アーカイブとアーカイブの解除は、その機能の `edit` に含める(Mem §3)。ユーザーは削除せず、所属を `suspended` にする。

**`rank` は表示の並び順で、上下関係ではない。** 権限の合成は和集合で行い、`rank` を判定に使わない(SolarOM の規約)。

**グループ**は1階層だけ(入れ子を禁止)。拠点とグループは多対多。

### 3-2. 割当

```
assignment
  id            割当の ID。経路の並び順にも使う
  principal     { type: user | team | collaboration(予約), id }
  role          ロールの key
  scope         { type: org | site_group | site | equipment(予約), id }   org のとき id は null
  exclusions    [ scope, ... ]   範囲から除く拠点やグループ(site_group / site だけ)
  expires_at    期限(ISO 8601。null なら期限なし)
  revoked_at    失効させた日時(null なら有効)
  granted_by    付与した人
  created_at
```

### 3-3. 判定の入力(スナップショット)

判定の関数は、次の形の値(スナップショット)とカタログを受け取る。アプリは自分のデータベースから、この形を作って渡す。

```
catalog                                 アプリごとに固定(ソースに書く)
  features   { feature: [action, ...] }       その機能グループで使える動詞
  roles      [ { key, rank, audience: internal | partner | owner, perms: { feature: [action, ...] } } ]

snapshot                                リクエストのたびに作る(またはキャッシュする)
  tenant_id
  now          判定の時刻(ISO 8601、時差つき)
  sites        [ { id, groups: [group_id, ...] } ]
  groups       [ { id } ]
  memberships  [ { user_id, status } ]
  teams        [ { id, members: [user_id, ...] } ]
  assignments  [ assignment, ... ]
```

- **スナップショットは1つのテナントのデータだけで作る。** `tenant_id` のテナントの拠点・グループ・所属・チーム・割当だけを入れ、ほかのテナントのものを混ぜない。アプリはセッションのテナント(§5)で作る。テナントを分けるのはアプリの読み出しの仕事で、部品はスナップショットの中だけを見る。だから、ほかのテナントの人を判定すれば `not_member` になり、ほかのテナントに同じ ID の拠点があっても混ざらない(判定テスト `tenants.json`)
- 拠点・グループ・チーム・割当の ID は、テナントの中で重ならなければよい(別のテナントに同じ ID があってよい)
- カタログは `validate_catalog` で確かめる。ロールの `perms` に、`features` に無い機能や動詞があればエラーにする。`member` と `audit` が無ければエラーにする。key の重複もエラーにする
- スナップショットに無い拠点・ロールを指していたら、判定はエラー(例外)にする。データの不整合は「操作できない」ではなく、プログラムの誤りとして扱うため

### 3-4. 判定の順序

Mem §7 を次のとおり当てはめる。

1. **所属を確かめる。** 対象のテナントで `status = active` の所属が無ければ、断る(理由 `not_member`)
2. **対象から範囲を解く。** 対象は `{type: org}` か `{type: site, id}` のどちらか。拠点なら、その拠点・その拠点が属するグループ・組織全体が該当する。組織全体の操作(ユーザー管理など)には、`org` の割当だけが該当する
3. **割当を集める。** 本人への直接の割当と、本人が入っているチームへの割当を集める。`principal.type = collaboration` の割当は**予約なので集めない**
4. **生きていない割当を落とす。** `expires_at <= now` のもの、`revoked_at <= now` のもの、`scope.type = equipment` のもの(予約)を落とす
5. **除外リストを当てる。** 対象の拠点が、割当の除外リストのどれか(拠点そのもの、またはその拠点が属するグループ)に当たれば、その割当を落とす
6. **和集合を取る。** 残った割当のロールが持つ権限をすべて合わせる
7. (共通の判定の**外**)データの状態による絞り込みは各アプリで行う。起票者ロック、オーナーには公開済みだけを見せること、アーカイブ済みを既定で隠すことなど

6 までが「その操作をしてよいか」、7 が「どのデータが見えるか」で、この2つを混ぜない(Mem §7)。

### 3-5. 判定の結果

```
evaluate(catalog, snapshot, user_id, permission, resource) → Decision
  allowed   true / false
  reason    null(allowed のとき)/ not_member / out_of_scope / no_permission
  paths     許した経路の配列(allowed のとき)。断ったときは空
```

| 理由 | いつ | 電力データ集計の文言(例) |
|---|---|---|
| `not_member` | 有効な所属が無い(招待中・停止中・所属なし)。運営側の人をお客様のテナントで判定したときもこれになる(サポートの閲覧は判定の外。§3-8) | (ログインできないので 401) |
| `out_of_scope` | 生きている割当のどれかがその権限を持っているが、この対象には届いていない | 「担当外の契約のため操作できません」 |
| `no_permission` | 生きている割当のどれもその権限を持っていない | 「閲覧ロールのため操作できません」「契約マスタの変更は管理者だけができます」 |

**経路**は、表示の文字列ではなく構造で返す。表示名はアプリごとに違うため。

```
path
  assignment_id
  via      { type: team, id } または null(直接の割当)
  scope    割当の範囲
  role     ロールの key
  direct   直接の割当なら true(SolarOM はこれを警告色で出す)
```

経路はスナップショットの `assignments` の順に並べ、同じ割当は1回だけ出す。

**ほかの関数**

| 関数 | 中身 | 使う場面 |
|---|---|---|
| `permissions_at(catalog, snapshot, user_id, resource)` | `{ feature: { action: [path, ...] } }`。SolarOM の `permissionsAt` と同じ形(経路は上の構造) | 権限の確認(逆引き)、画面のボタンをまとめて出し分ける |
| `sites_with(catalog, snapshot, user_id, permission)` | その権限が届く拠点の ID の配列(`sites` の順) | 電力データ集計の契約一覧(担当を先に並べる) |
| `check_guard(catalog, before, after, actor_user_id, guard_permission = "member.edit")` | 変更の前と後のスナップショットを比べて、違反の配列を返す。違反は `no_admin_left`(組織全体で `guard_permission` を持つ有効なメンバーがいなくなる)と `self_lockout`(操作した本人が `guard_permission` を失う、または停止になる) | ユーザー管理・割当の保存の前。電力データ集計の「自分を無効にできない」「自分を管理者以外にできない」「有効な管理者がいなくなる変更はできない」、Mem §9 の「最後の admin は降格できない」 |
| `validate_catalog(catalog)` | カタログの誤りの配列 | 各アプリのテスト |

### 3-6. 予約(拡張)

次のものは**名前とデータの形だけ**を決め、判定では効かせない。判定テストには「予約の割当は効かない」ことを入れる。実際に使う段階で、判定を変える版(メジャー)として出す。

| 予約 | 形 | 判定での扱い |
|---|---|---|
| 協力会社・オーナーのテナント | `tenant.kind`: `partner` / `owner`、ロールの `audience`: `partner` / `owner`(`own`・`operator` は §3-8 で使う) | 判定には使わない。電力データ集計の病院が自分で見る画面を作るときも `owner` を使う |
| テナント間の協業 | `principal.type = collaboration`、`collaborations`・`collaboration_members` の表(Mem §5) | 割当を集めない(§3-4 の 3) |
| 設備の範囲 | `scope.type = equipment` | 割当を落とす(§3-4 の 4) |
| テナントの管理者 | `membership.is_tenant_admin` | 判定には使わない(ゲスト側の管理者のために予約) |
| 課金しないテナント | `tenant.is_billable`(`partner` / `owner` は false。Mem §1) | 判定には使わない。協業で見える拠点は、持ち主(ホスト)のテナントでだけ数える |
| なりすましプレビュー | 監査ログの操作名 `view_as.started` | ― |

### 3-7. 課金との関係

両方のアプリとも**拠点数で課金する**。課金は判定の部品に入れない。

- **判定の外に置く。** 拠点数の上限など契約で止めるときは、各アプリが権限の判定とは別に確かめ、別の理由と文言で断る。判定に混ぜると、上限を超えたときに `no_permission` が返り、「閲覧ロールのため操作できません」のような誤った理由が出る。管理者が割当を直しても解決しない
- **課金に効く操作は専用の権限で守る。** 拠点を増やす操作(拠点の追加・アーカイブの解除)は請求を増やすので、各アプリのカタログで誰ができるかを明示する。取り込みなどで拠点が増える操作も、同じ権限で守る。電力データ集計は §7-2、SolarOM は段階4で決める(おすすめは管理責任者だけ)
- **拠点の増減を監査ログに必ず残す**(§4-2 の `site.*`。無期限)。「誰がいつ拠点を増やしたか」を請求の根拠として説明できるようにするため
- 人数では課金しないので、ユーザー・チームの数は制限しない。組織全体の割当があれば新しい拠点にも自動で権限が届くが、請求には影響しない
- **拠点はテナントごとに数える。** 運営側(§3-8)は請求のために、各テナントの拠点数と `site.*` の監査ログを、サポートの許可なしに見てよい(レポートなどの中身は見ない)
- 数え方(月末時点か月の最大か、アーカイブ済みを含むか、上限を超えたら止めるか請求を足すだけか)と、月ごとの拠点数の控えは請求の仕組みの側で持つ(§9)

### 3-8. テナントと運営側(当社)

**テナントの種類**(`tenant.kind`)

| 種類 | 中身 | 課金 |
|---|---|---|
| `own` | お客様の会社。電力データ集計なら省エネサービス会社、SolarOM なら O&M の会社 | する(拠点数) |
| `operator` | 運営側。アプリを運営する当社。アプリごとに1つだけ | しない |
| `partner`・`owner` | 予約(§3-6) | しない |

判定の部品は `kind` を使わない。運営側かどうかは、アプリがテナントの種類で見分ける。

**テナントの管理者**: お客様のテナントの中で、組織全体に `member.edit` を持つ人(電力データ集計の「管理者」ロール)。自分のテナントのユーザーと割当を管理する。最後の1人を守る決まり(`check_guard`)は、テナントごとのスナップショットで当てる。`membership.is_tenant_admin` は予約のまま(ゲスト側の管理者のため。§3-6)で、テナントの管理者の判定には使わない。

**テナントの一生**: 作る・止めるのは運営側だけ。

| 操作 | 中身 | 監査ログ |
|---|---|---|
| 作る | 契約のあとに作り、お客様の最初の管理者を招待する(所属は `invited`。受けると `active`) | `tenant.created`・`member.invited` |
| 変える | 名前・請求先など | `tenant.updated` |
| 止める | 解約・未払いなど。そのテナントの全員がログインできなくなり、セッションを消す。データは消さない(返却・削除は §9) | `tenant.suspended` |
| 再開する | 止めたテナントを戻す | `tenant.reactivated` |

**運営側の人**
- `operator` テナントに所属する。**お客様のテナントには所属せず、割当も持たない。** だから、お客様のメンバーの一覧に出ず、`check_guard` の数にも入らない
- 運営の操作(テナントの作成・停止、拠点数の確認、サポートの閲覧)をしてよいかは、`operator` テナントのスナップショットとカタログで判定する。機能グループはアプリが決める(例: `tenant`(view・create・edit)と `support`(view)。§7-6)
- **ログインの強さ**(2026-11-11 決定): Web の画面へのログインはお客様と同じ(電力データ集計ならパスワード+メールのコード)。ただし**運営側の人のセッションの期限は2時間**にする(お客様は8時間まで。§5)。運営側の人のメールアドレス(またはログインに使う外部のアカウント)には、その提供元の2段階認証を掛けておく(アプリの外の約束)
- **ログインのたびに2つ目の確かめ**(2026-11-13 決定): 運営側の人は、ログインのたびにパスワードのほかの確かめ(電力データ集計ならメールのコード)を通る。お客様向けの「この端末を覚える」のような、確かめを省く仕組みを運営側の人には使わせない(覚えさせず、覚えた端末があっても省かない)。OIDC のアプリ(SolarOM)は、認証サービスに同じことを求める形を段階4で決める
- **接続元を限れる**(2026-11-13 決定): 運営側の人が使ってよい接続元を、IP アドレスか CIDR の一覧で設定できるようにする(空なら限らない)。限ったときは、ログインも、ログインした後のリクエストも、範囲の外なら断る。ログインで断ったときは `auth.login.failed` に理由を残す(電力データ集計は `operator_ip`)
- **テナントの作成・停止・再開は、クラウドの権限で守られた運営側のコマンドだけで行い、Web の画面には置かない**(2026-11-11 決定。電力データ集計は今この形で、Google Cloud の権限で守っている)。Web の画面の運営側に要るのは、拠点数を見ることとサポートの閲覧だけになる
- 請求のため、各テナントの拠点数と `site.*` の監査ログは許可なしに見てよい(§3-7)

**サポートの閲覧**(運営側がお客様のデータを見る)
- お客様のテナントの管理者(組織全体に `member.edit` を持つ人)が、**期限を付けて許可する**。許可はいつでも取り消せる。許可の記録は `support_grants`(テナント・許可した人・作った日時・期限・取り消した日時)に置く
- **期限**(2026-11-11 決定): 許可する人が選ぶ。**既定は7日、上限は30日**。上限より先の期限は受け付けない。延ばすときは新しい許可を出す(前の許可は取り消すか、期限まで残す)
- 許可が生きている間(期限より前で、取り消されていない)だけ、`operator` テナントで `support.view` を持つ人が、そのテナントの画面を**見るだけ**で開ける。状態を変えるリクエストはすべて 403 にする。許可が切れたら、次のリクエストから見られない
- **閲覧中も見せない画面**(2026-11-13 決定): お客様の管理者だけの画面(ユーザー管理・監査ログ・サポートの許可)は、閲覧中も 403 にする。メールアドレスなど人の情報が載り、サポートに要らないため
- 判定の部品の外で確かめる。運営側の人はお客様のテナントに所属しないので、`evaluate` は `not_member` を返す。アプリは「許可が生きているか」と「運営側で `support.view` を持つか」の2つを確かめて開く。判定に混ぜない理由は課金と同じ(§3-7)で、お客様の割当を直しても説明できない結果が出ないようにするため
- 見始めるたびに `support_access.started` を残す(`host_tenant_id` = お客様のテナント、`actor_tenant_id` = `operator`)。お客様の管理者は、自分のテナントの監査ログでこれを見られる
- サポートの閲覧中のセッションは、見ているテナントと許可を持つ(§5)

## 4. 監査ログ

### 4-1. 項目

Mem §8 と同じ項目にする。

| 項目 | 中身 |
|---|---|
| `id` | 記録の ID(アプリが付ける) |
| `host_tenant_id` | どのテナントのデータへの操作か |
| `actor_user_id` | 操作した人。登録の無いメールアドレスでのログイン失敗など、人が分からないときは null |
| `actor_tenant_id` | 操作した人のテナント。ゲストのテナントからの操作と、運営側の操作(`operator` テナント。§3-8)を見分けるため。ふつうは `host_tenant_id` と同じ |
| `action` | 操作名(§4-2) |
| `target_type`・`target_id` | 対象(`user`・`assignment`・`team`・`email` など) |
| `before`・`after` | 変更の前と後(JSON のオブジェクト、または null) |
| `ip_address` | 接続元 |
| `created_at` | 日時(ISO 8601、時差つき) |

**秘密の値は入れない。** パスワード、パスワードのハッシュ、確認コード、トークン、セッションの値は `before`・`after` に入れない。部品の `validate_audit_event` は、これらに当たるキー(名前を単語に分けたとき、どれかの単語が `password`・`passwd`・`pwd`・`secret`・`token`・`session`・`otp`・`code` か、その複数形であるもの。入れ子・配列の中も見る。`verification_code` は秘密、`footprint` は秘密でない)があればエラーにする。細かな決まりは [spec/vectors.schema.md](../spec/vectors.schema.md) §6。

### 4-2. 操作名と必須の操作

| 操作名 | 必須か | 保存期間 |
|---|---|---|
| `auth.login.succeeded` / `auth.login.failed` | 必須 | 13か月 |
| `auth.logout` | 任意 | 13か月 |
| `auth.password.changed`(本人による変更) | 必須 | 13か月 |
| `auth.password.reset`(メールのコードでの再設定) | 必須 | 13か月 |
| `member.created` / `member.updated` / `member.suspended` / `member.reactivated` / `member.password_set`(管理者による再設定) / `member.invited` | 必須 | 無期限 |
| `assignment.created` / `assignment.updated` / `assignment.revoked` | 必須 | 無期限 |
| `role.changed`(画面上の「ロール」を変えたことのまとめ。割当の変化は上の `assignment.*` で必ず別に残す) | 任意 | 無期限 |
| `team.created` / `team.updated` / `team.archived` / `team.member_added` / `team.member_removed` | 必須(チームを使うアプリ) | 無期限 |
| `site.created` / `site.archived` / `site.unarchived`(拠点の増減。課金の根拠。§3-7) | 必須 | 無期限 |
| `tenant.created` / `tenant.updated` / `tenant.suspended` / `tenant.reactivated`(運営側によるテナントの作成・変更・停止・再開。§3-8) | 必須 | 無期限 |
| `support_access.granted` / `support_access.revoked`(お客様の管理者による許可と取り消し) / `support_access.started`(運営側が見始めた。§3-8) | 必須 | 無期限 |
| `<対象>.archived` / `<対象>.unarchived`(拠点以外) | 必須 | 無期限 |
| `collaboration.*`・`report.published`・`report.unpublished`・`view_as.started` | 予約 | 無期限 |
| `app.<名前>`(業務の記録。例: `app.upload.created`) | 任意 | 13か月 |

- 保存期間は Mem の決定(権限の操作は無期限、業務の記録は13か月)に合わせる。ログインの記録は件数が多いので13か月とする
- `auth.login.failed` は、パスワードが違う・コードが違う・コードを使い切ったなどの理由を `after.reason` に入れる。登録の無いメールアドレスのときは `actor_user_id` を null にし、対象を `email` にする
- **どのテナントの記録か**: `host_tenant_id` は操作の対象のデータを持つテナントにする。運営側の操作(テナントの作成・停止、サポートの閲覧)は、`host_tenant_id` を対象のお客様のテナント、`actor_tenant_id` を `operator` にする。テナントの分からない記録(登録の無いメールアドレスでのログインの失敗など)は、`host_tenant_id`・`actor_tenant_id` とも `operator` にする
- お客様の管理者が見られる監査ログは、`host_tenant_id` が自分のテナントのものだけ。運営側の人の名前は「運営側」とだけ出してもよい(アプリが決める)
- 部品の `make_audit_event(...)` は記録の形を作り、`validate_audit_event(event)` は形を確かめる(必須の項目、操作名が上の表にあるか `app.` で始まるか、秘密のキーが無いか)。保存・検索・画面は各アプリで作る

## 5. ログインした後の約束

ログインの作りはアプリごとに違ってよい(§1 の 3)。ただし、ログインした後は次の約束を守る。部品には入れず、各アプリのテストで確かめる。

**ログインとユーザーの結びつけ**
- `password`: メールアドレス(前後の空白を除き、小文字にそろえる)でユーザーを探す。電力データ集計は、パスワードに加えてメールのワンタイムコードを必須にしている
- `oidc`: 認証サービスの `iss`(発行元)と `sub`(利用者の ID)の組でユーザーを探す。メールアドレスは変わることがあるので、結びつけには使わない。最初のログインだけは、招待したメールアドレスと、認証サービスが確認済み(`email_verified = true`)としたメールアドレスが一致したときに `iss`・`sub` を結びつける。結びつけは `user_identities(user_id, issuer, subject)` に置く
- どちらの場合も、有効な所属(`active`)が無ければログインさせない。所属するテナントが止まっているときもログインさせない(§3-8)
- メールアドレスは全テナントで重ならないので、メールアドレスや `iss`・`sub` で探せばユーザーは1人に決まる。所属が1つなら、そのテナントに入る。所属を複数持てるアプリは、ログインのあとにテナントを選ばせる(電力データ集計は1人1社なので選ばない)

**セッション**
- サーバー側に持つ。値は推測できない乱数(32 バイト以上)にし、データベースにはそのハッシュだけを置く
- Cookie は `HttpOnly`・`SameSite=Lax`。https で配信するときは `Secure` も付ける
- 期限はログインからの絶対時間で決め、延長しない。長さはアプリが決める(上限8時間。電力データ集計は8時間)。**運営側の人は2時間**(§3-8)
- 運営側の人は、ログインのたびに2つ目の確かめを通る(端末を覚えて省かない)。接続元を限ったときは、セッションのあるリクエストでも接続元を確かめる(§3-8)
- セッションは `user_id` と `active_tenant_id`(いま操作しているテナント)を持つ。運営側の人がサポートの閲覧をしている間は、見ているテナントと許可(`support_grants` の行)も持つ。`active_tenant_id` は `operator` のまま(§3-8)

**セッションを消すとき**: 次の変更をしたら、その人のセッションをすべて消す。
- 所属を停止したとき、メールアドレスを変えたとき、その人の割当(またはその人が入っているチームの割当、その人のチームの出入り)を変えたとき、管理者がパスワードを再設定したとき、本人がメールのコードでパスワードを再設定したとき
- 本人がパスワードを変えたときは、ほかのセッションを消す
- テナントを止めたときは、そのテナントに所属する全員のセッションを消す
- サポートの許可を取り消したときや期限が来たときは、その許可で見ている運営側の人の閲覧を終える(閲覧はリクエストのたびに許可を確かめるので、次のリクエストで切れる)

**テナントを分ける**
- **データの読み書きは、すべてセッションのテナントに限る。** サポートの閲覧中は、見ているテナントに限る
- テナントの ID は URL や入力から受け取らず、セッションから決める
- 対象(拠点・ファイル・ユーザーなど)を ID で開くときは、そのテナントのものかを先に確かめる。ほかのテナントのものなら、あることを知らせないために 404 にする(403 にしない)
- 各アプリのテストで、2つのテナントに同じ ID のデータを作り、ほかのテナントのものが見えない・変えられないことを、全部の画面と API で確かめる

**判定のしかた**
- 権限の判定はサーバー側で、リクエストのたびに行う。画面での出し分け(ボタンを灰色にするなど)は同じ判定の結果を使うが、それだけで守らない
- 端末に置いた権限(SolarOM のオフライン入力など)は読み取りの判定にだけ使い、書き込みはサーバー側で必ず判定し直す(SolarOM 権限管理画面設計 §10 の決定)
- 状態を変えるリクエストは、`Origin` ヘッダーが自分と違えば 403 にする(CSRF 対策)
- ログインしていなければ 401、権限が無ければ 403

**ログインの記録**: §4-2 の `auth.*` を残す。

## 6. 部品の配り方と版

### 6-1. 版の番号

`MAJOR.MINOR.PATCH` で付け、このリポジトリに `vX.Y.Z` のタグを付ける。

| 上げる番号 | いつ |
|---|---|
| MAJOR | 今ある判定テストの正解が変わる。関数の名前・引数・戻り値の形が変わる。予約を実際に効かせる |
| MINOR | 判定テストを足す(今ある正解は変わらない)。関数や監査ログの操作名を足す |
| PATCH | 文書の直し、正解の変わらない中の直し |

Python 版と JS 版は同じ番号で一緒に出す。どちらも同じ判定テストを通らなければタグを付けない。

### 6-2. 写し(vendoring)

各アプリには、このリポジトリのタグの中身を**写し**として置く。private なリポジトリを pip や npm で取り込むと、サーバーや Workers のビルドに GitHub の認証が要るため。写しなら、動かすときにほかのリポジトリへ依存しない。

```
<アプリの中の置き場所>/auth_foundation/
  VERSION          写した版(例: 1.0.0)
  MANIFEST.json    写したファイルとその SHA-256、もとのタグとコミット
  (部品のファイル) Python 版なら auth_foundation/*.py、JS 版なら auth-foundation.mjs
  vectors/*.json   判定テスト
  verify_vendor.py / verify-vendor.mjs   確かめ用のコード
  .gitattributes   取り込んだリポジトリで git が改行を変えないようにする(Windows の autocrlf でハッシュが変わるため)
```

- 写しは `tools/vendor.py --lang python|js --dest <置き場所>` で作る(このリポジトリのタグを checkout した状態で実行する)。**写しを手で直さない**
- 各アプリのテストには次の2つを入れる。(1) 写したファイルの SHA-256 が `MANIFEST.json` と一致する、(2) 写した判定テストを写した部品がすべて通る。手で直すと (1) で落ちる
- アプリ側で直したいことが見つかったら、このリポジトリで直して版を上げ、写し直す
- **SolarOM の注意**: `デモアプリ/` はまるごと公開される(SolarOM の CLAUDE.md の規約)。写しはサーバー側(Workers)のコードの置き場所に置き、`デモアプリ/` の下には画面で使う `auth-foundation.mjs` だけを置く(判定テストや MANIFEST を公開しない)。置き場所は SolarOM のセッションで決める

### 6-3. 判定テストの形

```json
{
  "name": "pda-creator",
  "description": "電力データ集計の作成者: 担当契約は操作でき、担当外は閲覧だけ",
  "catalog": { ... },
  "snapshot": { ... },
  "cases": [
    { "call": "evaluate",
      "args": { "user_id": "sakusei1", "permission": "report.edit", "resource": { "type": "site", "id": "B" } },
      "expect": { "allowed": false, "reason": "out_of_scope", "paths": [] } }
  ]
}
```

細かな決まり(エラーの種類と確かめる順、時刻の形、誤りの並び順)は [spec/vectors.schema.md](../spec/vectors.schema.md) に書く。

- `call` は §3-5 と §4 の関数の名前。エラーになることを確かめるときは、`expect` の代わりに `expect_error` にエラーの種類を書く(`unknown_site`・`unknown_role` など)
- 判定テストは少なくとも次を含める: 和集合、直接の割当とチーム経由、グループの多対多、除外リスト(拠点とグループ)、期限と失効の境目(`now` と同じ時刻は「過ぎた」とする)、予約の割当が効かないこと、停止中・招待中のユーザー、断る理由の3種類、経路の並び順、`check_guard` の2種類の違反、`validate_audit_event` の秘密のキー、テナントが分かれていること(ほかのテナントのスナップショットでは `not_member`、同じ ID の拠点が混ざらない、`check_guard` がテナントごと、運営側の監査ログ)。さらに、電力データ集計の4人(§7-4)と SolarOM のデモデータ(`perm-data.js` の割当 a1〜a11)を当てはめたものを入れる

## 7. 電力データ集計への当てはめ

### 7-1. テナントとユーザー

- **テナントは SaaS を契約する会社**(病院向けに月次レポートを作る省エネサービス会社。`kind = own`)。会社ごとにデータを分ける。病院はレポートを受け取る側で、テナントではない(病院が自分で見る画面を作るときは予約の `owner`)
- 運営側(当社)は `operator` テナント(§3-8、§7-6)
- ユーザーID はそのまま `user.id`、`auth_provider` は `password`。ユーザーとメールアドレスは全テナントで重ならない(ログインがメールアドレスでユーザーを探すため)
- **1人1社。** 所属は1人1つで、ログインするとその所属のテナントに入る
- 有効 / 無効は、所属の `active` / `suspended` に当たる
- 今の「契約」は、共通の言葉では**拠点(`site`)**に当たる。共通仕様の機能グループ `contract`(Mem の「契約・請求」)とは別のもので、電力データ集計はこの機能グループを使わない。グループ(`site_group`)は使わない。契約ID はテナントの中で重ならなければよい
- 拠点(契約)の数はテナントごとに数えて請求する(§3-7)

### 7-2. 機能グループ

| 機能グループ | 表示名 | 動詞 | 今の操作 |
|---|---|---|---|
| `report` | 月次レポート | `view`, `edit` | `view`: 契約一覧・月次作業画面・履歴を見る。`edit`: 取込・確認済みにする・コメント保存・下書きに戻す・PDF 出力 |
| `site_master` | 契約マスタ | `view`, `create`, `edit` | `view`: 見る。`edit`: 保存(アーカイブとその解除を含む)。`create`: 契約の追加。追加とアーカイブの解除は課金に効くので管理者だけ(§3-7)。今は契約を画面で増やせない(`contracts.json` で持つ)が、作るときはこの権限で守る |
| `member` | ユーザー管理 | `view`, `create`, `edit` | ユーザー管理(`/users`) |
| `audit` | 監査ログ | `view` | (画面は今は無い) |

### 7-3. ロールと割当

| ロール | 権限 | 割当 |
|---|---|---|
| `admin` 管理者(テナントの管理者。§3-8) | すべて | `org` に1つ |
| `creator` 作成者 | `report.view`・`report.edit` | **担当契約ごとに** `site` に1つ ずつ |
| `viewer` 閲覧 | `report.view`・`site_master.view` | `org` に1つ |

**作成者は2種類の割当で表す。** 「担当契約ごとの `creator`」に「`org` の `viewer`」を足す。和集合なので、担当契約は操作でき、担当外は閲覧だけになり、今の `auth.can_operate` と結果が一致する。

**画面の「ロール」は今の形のまま残す。** ユーザー管理の画面で選ぶのは、今と同じ「ロール」と「担当契約」の2つ。保存するときに、この2つから割当を作り直す。画面の「ロール」は `users.role` に残す。理由は、担当契約が0件の作成者は割当だけを見ると閲覧と区別できず、断る理由の文言(「担当外の契約のため」)と一覧の表示を今と同じにできないため。

**断る理由の文言**: `out_of_scope` →「担当外の契約のため操作できません」。`no_permission` のときは、画面の「ロール」が作成者なら「担当外の契約のため操作できません」、閲覧なら「閲覧ロールのため操作できません」とする。契約マスタの保存とユーザー管理では「契約マスタの変更は管理者だけができます」のように操作ごとの文言を使う。どれも今の文言と同じ。

### 7-4. 今のデモ用ユーザーの割当

4人ともデモの会社のテナント(ID `demo`)に入れる。

| ユーザーID | 画面のロール | 割当 |
|---|---|---|
| `admin` | 管理者 | admin @ org |
| `sakusei1` | 作成者 | creator @ A・C・E、viewer @ org |
| `sakusei2` | 作成者 | creator @ B・D・F、viewer @ org |
| `etsuran` | 閲覧 | viewer @ org |

### 7-5. 今の作りとの違い(移行で足すもの)

移行は3つに分けて進める(§8 の段階 3a〜3c)。新しく足す表(割当・監査ログ)が最初からテナントを持つように、テナントを先に入れる。

**3a. 全部の表にテナントを持たせる**(デモの会社 `demo` の1つだけで動かし、振る舞いは変えない)
- テナントの表(`tenants`: ID・名前・種類・状態・請求先など)と所属の表(`memberships`: ユーザー・テナント・状態)を足す。今の `users.active` は所属の状態に移す。1人1社なので、所属はユーザーごとに1つだけ作れるようにする
- **データを持つ表のすべてに `tenant_id` を足す**: `contracts`・`readings`・`uploads`・`findings`・`comments`・`pdf_exports`・`user_contracts`(3b で割当に置き換える)。`sessions` には `active_tenant_id` を足す。ユーザー(`users`)とログインの途中の表(`login_codes`・`code_issues`)はユーザーに付くので、テナントを持たせなくてよい
- 重ならない決まりをテナントの中にする(例: 契約ID は `(tenant_id, 契約ID)` で重ならない)。メールアドレスは全体で重ならないまま
- ファイルの置き場所もテナントで分ける(`data/raw/<テナント>/…`・`outputs/<テナント>/…`)
- データベースを読み書きする関数は、すべてテナントを引数に取る(渡し忘れを、呼び出しの形で防ぐ)。ID で開くものはテナントが合わなければ 404(§5)
- 帳票やメールに出す社名(今の `COMPANY_NAME`)をテナントの設定にする
- 今のテスト(slow 込みで690件)がそのまま通ることと、**2つのテナントに同じ契約ID を作り、ほかのテナントのものが全部の画面と API で見えない・変えられない**ことを確かめる

**3b. 割当と監査ログ**(共通の形に移す。振る舞いは変えない)
- 割当の表(`assignments`。テナントを持つ)を足す。`user_contracts` は割当から作り直せるので、移行の中で割当に置き換える(置き換え方は電力データ集計のセッションで決める)
- 監査ログの表(`audit_logs`)を足し、§4-2 の必須の操作を記録する(`host_tenant_id`・`actor_tenant_id` の決まりは §4-2)。今の「最後に誰が」の列(`uploaded_by` など)は画面に出すためのものなので、そのまま残す
- セッションを消す条件(§5)は今の作りでほぼ満たしている(ロールや担当契約を変えたら消している)
- 契約(拠点)の追加・アーカイブを画面で作るときは、`site.*` を監査ログに残す(§3-7)。今は画面に無いので、移行では足さない
- 振る舞いは変えない。今のテストがそのまま通ることで確かめる

**3c. 運営側**(新しい振る舞い。§3-8・§7-6)
- `operator` テナントと運営側の人、テナントの作成・変更・停止・再開、最初の管理者の招待
- サポートの許可(`support_grants`)を出す・取り消す画面(お客様の管理者)と、サポートの閲覧(運営側。見るだけ)
- テナントを止めたらログインできず、セッションが消えること。許可が切れたら見られないこと。閲覧中に書き込めないこと。それぞれをテストで確かめる

### 7-6. 運営側のカタログ(おすすめ)

運営側(`operator` テナント)は、お客様のテナントとは**別のカタログ**で判定する。お客様の「管理者」(すべての権限)が運営の権限を持たないようにするため。最後の形は電力データ集計のセッションで決める。

| 機能グループ | 動詞 | 中身 |
|---|---|---|
| `tenant` | `view`, `create`, `edit` | テナントの一覧と拠点数を見る、作る、変える(止める・再開するを含む) |
| `support` | `view` | 許可のあるテナントを見る(サポートの閲覧) |
| `member` | `view`, `create`, `edit` | 運営側の人の管理 |
| `audit` | `view` | 運営側の監査ログ |

| ロール | 権限 |
|---|---|
| `operator_admin` 運営の管理者 | すべて |
| `support` サポート | `tenant.view`・`support.view` |

テナントの作成・停止・再開は運営側のコマンドだけで行う(§3-8。2026-11-11 決定)ので、Web の画面で使う運営側の権限は `tenant.view` と `support.view` だけになる。`tenant.create`・`tenant.edit` は、コマンドを動かす人を Google Cloud の権限で限ることに当たる(電力データ集計の今の作り: `add-company`・`suspend-company`・`reactivate-company`・`invite`・`site-counts`・`site-limit` など)。
